## Caso 1 — El problema de la lista blanca (whitelist)

> [!question] Situación
> Un sistema tiene una lista de 5.000 identificadores autorizados (una "whitelist": clientes habilitados, cuentas verificadas, lo que sea) y necesita revisar 20.000 transacciones nuevas para decidir cuáles corresponden a identificadores autorizados. Es, literalmente, el caso que usa Sedgewick para motivar por qué hacen falta algoritmos eficientes de búsqueda:

> [!quote] El planteo original
> "Solving the whitelist problem for a large number of inputs is not feasible without efficient algorithms such as binary search." *Fuente: [[Algorithms-4th-Edition-By-Robert Sedgewick and Kevin Wayne]], cap. 1.1.*

**Dos estrategias posibles:**

```python
# Estrategia 1: fuerza bruta — para cada transacción, revisar toda la whitelist
cnt = 0
for t in transacciones:
    if t in whitelist_como_lista:      # búsqueda lineal, O(n) cada vez
        cnt += 1

# Estrategia 2: ordenar la whitelist una vez, después usar bisect (búsqueda binaria)
import bisect
wl_ordenada = sorted(whitelist)
cnt2 = 0
for t in transacciones:
    pos = bisect.bisect_left(wl_ordenada, t)
    if pos < len(wl_ordenada) and wl_ordenada[pos] == t:
        cnt2 += 1
```

Verificado en este entorno, con 5.000 identificadores y 20.000 transacciones (ambas estrategias coinciden: 530 transacciones autorizadas):

| Estrategia | Tiempo |
|---|---:|
| Fuerza bruta (búsqueda lineal, 20.000 veces) | 263,5 ms |
| Ordenar la whitelist una vez | 0,3 ms |
| Buscar las 20.000 transacciones (binaria) | 3,4 ms |
| **Total ordenar + binaria** | **3,7 ms** |

> [!important] 72 veces más rápido, resolviendo exactamente lo mismo
> Ordenar una sola vez y después usar búsqueda binaria resolvió el mismo problema **72 veces más rápido**. Es el mismo razonamiento de [[04 - Busqueda y ordenamiento|la Sección 1.3 de la clase]] —¿cuántas veces se va a buscar?— llevado a una escala donde la diferencia ya deja de ser una curiosidad de laboratorio y se vuelve una decisión de diseño real: con 20.000 transacciones a verificar, un sistema que use fuerza bruta puede directamente no dar abasto donde uno que ordene primero no tiene problema.

## Caso 2 — ¿Selection sort realmente no le importa cómo vengan los datos?

> [!question] Situación
> La bibliografía afirma algo fuerte sobre selection sort: que su comportamiento **no depende en absoluto** del orden de entrada, a diferencia de insertion sort. ¿Se sostiene esa afirmación con números reales, o es una simplificación?

> [!quote] La afirmación a poner a prueba
> "Running time is insensitive to input [...] the running time [of insertion sort] depends on the initial order of the items in the input." *Fuente: [[Algorithms-4th-Edition-By-Robert Sedgewick and Kevin Wayne]], cap. 2.1.*

Instrumentando ambos algoritmos para contar comparaciones reales, sobre 500 elementos, en tres escenarios (verificado en este entorno):

| | Aleatoria | Ya ordenada | Orden invertido |
|---|---:|---:|---:|
| **Selección** — comparaciones | 124.750 | 124.750 | 124.750 |
| **Inserción** — comparaciones | 64.674 | 499 | 124.750 |

$n(n-1)/2$ para $n=500$ da exactamente **124.750** — el número de comparaciones de selección, **idéntico en los tres escenarios**, sin ninguna excepción. Insertion sort, en cambio, va de 499 comparaciones (casi instantáneo) a 124.750 (su peor caso), dependiendo enteramente de cómo vinieran los datos.

> [!important] La afirmación se sostiene exactamente
> No es una aproximación ni una simplificación pedagógica: selection sort hace **la misma cantidad exacta** de comparaciones sin importar el orden de entrada, porque su lógica —"buscar el mínimo entre lo que queda"— revisa siempre todos los candidatos restantes, encuentre el mínimo rápido o no. Es la contracara de lo que hace bueno a insertion sort en datos parcialmente ordenados (Caso 3): selection sort no tiene forma de "darse cuenta" de que los datos ya vienen ordenados y aprovecharlo.

## Caso 3 — ¿Cuántas "correcciones fuera de orden" hacen falta para notar la diferencia?

> [!question] Situación
> Sedgewick conecta el rendimiento de insertion sort con un concepto preciso: las **inversiones** (pares de elementos fuera de orden entre sí). Un libro contable que se carga cronológicamente pero después recibe unas pocas correcciones tardías es un ejemplo perfecto de datos con **pocas** inversiones — casi ordenados, pero no del todo.

> [!quote] La afirmación a verificar
> "The number of exchanges used by insertion sort is equal to the number of inversions in the array." *Fuente: [[Algorithms-4th-Edition-By-Robert Sedgewick and Kevin Wayne]], cap. 2.1 (Proposición C).*

Se construyó una lista de 300 elementos ya ordenada, con exactamente **8 correcciones** (8 pares de asientos adyacentes intercambiados entre sí — simulando 8 registros cargados fuera de orden), y se la comparó con una lista completamente al azar del mismo tamaño. Se contaron las inversiones por fuerza bruta (revisando todos los pares) y, por separado, los intercambios que hizo insertion sort (verificado en este entorno):

| | Inversiones (fuerza bruta) | Intercambios de inserción | ¿Coinciden? |
|---|---:|---:|---|
| Casi ordenada (8 correcciones) | 8 | 8 | ✓ |
| Aleatoria | 20.125 | 20.125 | ✓ |

Los números **coinciden exactamente** en ambos casos, tal como predice la Proposición C. Y el efecto en tiempo real es dramático:

| | Tiempo (insertion sort) |
|---|---:|
| Casi ordenada (8 correcciones) | 0,018 ms |
| Aleatoria | 0,808 ms |

**46 veces más lento** sobre datos completamente al azar, con el mismo `n`. La diferencia no es "insertion sort es rápido a veces" — es una consecuencia matemática exacta y predecible de cuántos pares están fuera de orden, no una casualidad de esta corrida en particular.

## Caso 4 — Cuando mover un dato es caro: minimizar movimientos, no solo comparaciones

> [!question] Situación
> Sedgewick destaca que selection sort hace, como máximo, `n − 1` **intercambios** — muy pocos comparado con burbuja o inserción. ¿Cuánta diferencia hace eso en la práctica, si mover cada elemento tuviera un costo real (por ejemplo, reescribir un registro grande en disco en vez de mover un número en memoria)?

> [!quote] La propiedad a cuantificar
> "Data movement is minimal [...] no other method that we consider has this property." *Fuente: [[Algorithms-4th-Edition-By-Robert Sedgewick and Kevin Wayne]], cap. 2.1.*

Contando movimientos totales (intercambios en burbuja/selección, corrimientos en inserción) sobre 400 elementos al azar (verificado en este entorno):

| Algoritmo | Movimientos totales |
|---|---:|
| Burbuja | 39.973 |
| **Selección** | **392** |
| Inserción | 39.973 |

> [!important] Más de 100 veces menos movimientos, con la misma complejidad Big O
> Los tres algoritmos son O(n²) — la misma clasificación teórica. Pero selección hizo **392** movimientos de datos contra casi 40.000 de las otras dos: más de 100 veces menos. Si cada "movimiento" implicara reescribir un registro pesado (no un número suelto), esta diferencia sería la que decide qué algoritmo usar — aunque las tres opciones tengan, en el papel, exactamente la misma notación Big O. Es la demostración concreta de algo que ya señala [[ordenamiento burbuja, selección e inserción]]: Big O describe el crecimiento, no todos los costos reales.

## Caso 5 — Por qué la estabilidad no es un detalle académico: un libro de ventas

> [!question] Situación
> Essential Algorithms explica que un ordenamiento estable permite ordenar por varias columnas sin perder el orden anterior. ¿Qué pasa exactamente, en un caso concreto, si el ordenamiento **no** es estable?

Se armó un libro de ventas chico, cargado en orden cronológico, con dos vendedoras (Ana y Beto). Se lo ordenó por vendedor de dos formas: con `sorted()` de Python (estable) y con una variante de selection sort **modificada a propósito** para ser inestable (ante un empate, se queda con el último candidato visto en vez del primero — sigue produciendo un resultado igual de "bien ordenado" por vendedor, pero no respeta el orden original entre empatados).

Resultado, verificado en este entorno:

**Con `sorted()` (estable)** — las fechas de Ana quedan `[1, 3, 4, 6]`, en el mismo orden cronológico en que estaban antes de ordenar por vendedor.

**Con la variante inestable** — las fechas de Ana quedan `[6, 1, 4, 3]`: el mismo conjunto de ventas, agrupadas igual de correctamente por vendedor, pero **completamente desordenadas por fecha** dentro del grupo.

> [!important] Los dos resultados son "correctos" — y sin embargo, muy distintos
> Ambos ordenamientos cumplen exactamente lo que se les pidió ("agrupar por vendedor") — verificado: la secuencia de nombres de vendedor es **idéntica** en los dos resultados. La diferencia está enteramente en algo que nadie pidió explícitamente pero que se esperaba **implícitamente**: que el orden cronológico previo no se perdiera dentro de cada grupo. Ese es, exactamente, el riesgo que describe la bibliografía: *"programmers who are unfamiliar with stability are surprised [...] by the way an unstable algorithm seems to scramble the data."* *Fuente: [[Algorithms-4th-Edition-By-Robert Sedgewick and Kevin Wayne]], cap. 2.5.* Desarrollo conceptual completo en [[estabilidad de un ordenamiento]].

## Caso 6 — Timsort en acción: medir su ventaja "adaptativa"

> [!question] Situación
> Se dijo en la clase que Timsort detecta tramos ya ordenados (*runs*) y los aprovecha. ¿Se puede medir directamente cuánto mejora el tiempo de `sorted()` a medida que los datos vienen más ordenados, sin cambiar nada más que el porcentaje de desorden?

Se generaron listas de 200.000 elementos, todas empezando de una versión ya ordenada, revolviendo al azar distintos porcentajes de sus posiciones (0 % = completamente ordenada, 100 % = completamente al azar). Tiempo de `sorted()` sobre cada una (verificado en este entorno):

| % de datos desordenados | Tiempo de `sorted()` |
|---:|---:|
| 0 % | 0,93 ms |
| 1 % | 2,71 ms |
| 5 % | 4,57 ms |
| 10 % | 5,89 ms |
| 25 % | 8,59 ms |
| 50 % | 12,20 ms |
| 100 % | 16,78 ms |

> [!important] El mismo algoritmo, hasta 18 veces más rápido según cuánto orden ya traían los datos
> No hay ningún cambio de código entre una fila y otra — es exactamente la misma llamada a `sorted()`. La única diferencia es cuánto orden ya tenían los datos de entrada, y el tiempo responde de forma prácticamente monótona a eso. Esta es la propiedad "adaptativa" de Timsort hecha número: aprovecha los tramos ya ordenados que detecta (los *runs*) en vez de tratar toda la entrada como si viniera completamente al azar, algo que ninguno de los tres ordenamientos elementales de esta clase sabe hacer (salvo, parcialmente, la burbuja optimizada e inserción — ver [[ordenamiento burbuja, selección e inserción]]).

## Caso 7 — Verificando (y refutando) una afirmación de la bibliografía

> [!question] Situación
> Uno de los libros de la bibliografía del curso afirma que el ordenamiento nativo de Python "is quicksort implemented in C". Ya se señaló en la clase que esto es incorrecto —Python usa Timsort—, pero **decir** que es incorrecto no es lo mismo que **demostrarlo**. ¿Se puede verificar empíricamente, sin más que código?

> [!quote] La afirmación en cuestión
> "The built-in sort, which is quicksort implemented in C, runs the fastest." *Fuente citada (y a refutar): [[Data Structures and Algorithms with Python]], cap. 9.*

**La idea:** quicksort "de libro de texto" (pivote = primer elemento) tiene un punto débil conocido — sobre datos **ya ordenados**, cada llamada recursiva solo logra separar un elemento del resto, en vez de partir el problema por la mitad. Eso lo degrada de O(n log n) a O(n²), y además hace que la recursión llegue a una profundidad de `n` niveles en vez de $\log_2 n$. Si el `sorted()` de Python fuera real y llanamente ese quicksort ingenuo, debería mostrar el mismo comportamiento patológico sobre datos ya ordenados.

```python
def quicksort_ingenuo(lista):
    """Quicksort de libro de texto, pivote = primer elemento."""
    if len(lista) <= 1:
        return lista
    pivote = lista[0]
    menores = [x for x in lista[1:] if x < pivote]
    mayores = [x for x in lista[1:] if x >= pivote]
    return quicksort_ingenuo(menores) + [pivote] + quicksort_ingenuo(mayores)
```

Verificado en este entorno, sobre datos **ya ordenados**:

| n | `quicksort_ingenuo` | `sorted()` de Python |
|---:|---:|---:|
| 500 | 4,37 ms | 0,005 ms |
| 1.000 | 12,15 ms | 0,007 ms |
| 2.000 | 40,24 ms | 0,011 ms |
| 3.000 | **`RecursionError`** — no llega a terminar | 0,016 ms, sin errores |

> [!important] La refutación, con evidencia
> El quicksort ingenuo no solo se vuelve progresivamente más lento sobre datos ordenados (4,4 ms → 12,2 ms → 40,2 ms, la firma de un O(n²) degenerado) — a partir de 3.000 elementos **directamente se rompe**, porque la recursión llega a una profundidad de miles de niveles y excede el límite de Python. `sorted()`, sobre los mismos 3.000 elementos ya ordenados, tarda 0,016 milisegundos, **sin ningún error**. Si el ordenamiento nativo de Python fuera realmente el quicksort ingenuo que describe esa fuente, tendría que mostrar el mismo colapso — y no lo muestra, porque no lo es. Es exactamente el comportamiento que predice la propiedad "adaptativa" de Timsort del Caso 6: datos ya ordenados son, para Timsort, el mejor caso posible (O(n)), no el peor.
